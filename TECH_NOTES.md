# TECH_NOTES — the engine port and how it was verified

What Dispatch Lab's engine is, what it had to reproduce exactly, and the record of the checks. The page's own README covers what it shows; `tests/README.md` lists the checks.

## 1. What the page reproduces

The challenge's runner (`src/tbrain-simulation.py` on `main`) loads `data/maps/neufrankfurt_19agents.json` with `src/scenario_loader.py` and steps flatland-rl's `RailEnv` with one controller until every train is done or the map's last step (1,248) has passed. The score is the sum of every step's rewards. For Köln the tools run the same runner with the same loader settings on `data/maps/kk_36agents.json` instead; the loader scales the penalties to that map's 1,710 steps.

| Item | Value |
|---|---|
| Challenge | VictorPflueger/mobilitychallenge, `main` at 5303697 (28 Oct 2026) |
| Map: Neu-Frankfurt | `neufrankfurt_19agents.json`, 100 × 60 cells, 19 trains, 59 intermediate stops, 1,248 steps, sha256 `8b7a7b6e…bea0d5228` |
| Map: Köln | `kk_36agents.json`, 120 × 100 cells, 36 trains, 108 intermediate stops, 1,710 steps, sha256 `b308ff99…cfce02bb` |
| Environment | flatland-rl 4.2.2 on Python 3.13.18 (the challenge's `uv.lock`) |
| Loader settings | `remove_agents_at_target=True`, acceleration 0.3, braking −0.5, malfunctions off |
| Rewards | `src/rewards_fix.py` (`DefaultRewards`) with `get_scaled_penalties(max_episode_steps, "balanced")`: crash 0.75 × steps × speed, stop not served 0.40 × steps, cancellation 4 × (travel time + 0.30 × steps), late at a stop 0.5 per step, early departure 1.75 per step, late at the target 1 per step. Neu-Frankfurt: crash 936, lost stop 499.2, cancellation buffer 374.4; Köln: 1,282.5, 684 and 513 |

The challenge also ships `src/speed_counter_fix.py` and `src/agent_utils_fix.py`, but the runner does not import them: flatland's own `SpeedCounter` and `EnvAgent` run, and the port follows those.

With the page's **Malfunctions** switch on, the tools record every run a second time with the loader's malfunctions (`scenario_loader.load(..., use_malfunctions=True)`) and the environment's random generator seeded with `MALFUNCTION_SEED` (1, `tools/maps.py`) before the episode; section 4d.

## 2. The engine (`js/engine/`)

A line-by-line port of `RailEnv.step` and what it calls, for the parts these scenarios use:

- **Speed counter**: a train's speed is `1 / round(1 / speed)`, so Neu-Frankfurt's RB speed 0.8 becomes 1.0 and the S-Bahn's 0.6 becomes 0.5 (on Köln the express trains' 0.8 and the local trains' 0.6 likewise); distance accumulates modulo 1; a cell is left when distance + speed ≥ 1.
- **Actions**: `check_action_on_agent` on the transition map: LEFT or RIGHT where there is no such branch becomes MOVE_FORWARD, a move with no track ahead becomes STOP_MOVING, and a cell with a single way out decides the direction; a train speeds up on MOVE_FORWARD only when that was the action given.
- **State machine**: `envs/step_utils/state_machine.py`, all seven states, with the signals computed in the same order.
- **Motion check** (`envs/step_utils/motion_check.py`, Bochatay 2024): the graph of who wants which resource, conflicts resolved with the lower index winning, swaps and deadlocks stopped. A level-free crossing is two resources, one per axis, so trains crossing at different levels never conflict.
- **Distance maps**: `DistanceMap._distance_map_walker`, a breadth-first walk backwards from each target over the transitions, and `get_shortest_paths` for the travel time on the shortest path, including its quirk at a dead end (an empty path, so a travel time of 0).
- **Episode end**: when every train is done, or at the map's last step (1,248 or 1,710), every train gets its end-of-episode reward and the episode is over; a train at its target is removed from the map.
- **A train placed on its own destination** (Köln's six S-Bahn loops, which start and end on the same cell): the arrival check (`update_if_reached`) runs in the step the train moves onto the map, so it is done and removed in that step, and all its stops are booked as lost. A loop that never sets off pays the cancellation as well.
- **Rewards**: `DefaultRewards.step_reward` and `_agent_done_or_max_episode_steps_reward` with their bookkeeping of arrivals, departures and states per waypoint, including the assertion that rejects a revisited waypoint.

Each reward is kept with its Python type (int or float), because the score is a sum of both.

## 3. Python semantics the scores depend on

Matching flatland's floats to the last digit needed CPython's own behaviour in three places (`js/engine/py.js`):

- **`sum()`** in CPython 3.13: an exact integer fast path, the first float added plainly, later floats with Neumaier compensation, the compensation added at the end. The runner's total and `cumulate()` both use it; the baseline's score is −74,022.59999999998, not −74,022.6.
- **Set iteration order** for small ints (the hash table's 8 slots, linear probes, perturbation, resizing): `MotionCheck` iterates a set of train handles when it stops deadlocked trains, and the order decides who stops first.
- **`round()`** rounds half to even (`1 / 0.4` = 2.5 → 2).

(A fourth trap, outside the engine: flatland's `RailEnvActions` is a `fastenum` that never equals a plain int and cannot be passed to `int()`; the tools record `action.value`.)

`tests/engine.mjs python` checks the first three against CPython on 11,010 random inputs (6,000 sums, 5,000 set orders, 10 roundings), with pools sized for both maps (sums of up to 45 terms, sets of handles up to 35).

## 4. The controllers (`js/controllers/`)

- **Baseline**: `OrderedController.act` on a tree observation of depth 2; only the children's `dist_min_to_target` at depth 1 matter. The smallest distance of at least 0 wins (`min_gt` tests ≥, whatever its docstring says), ties go to the last index, and with no branch at all (every distance infinite) the last index is the backward one, which maps to STOP_MOVING.
- **Optimized**: `PlannerController` v2 (`n_orders=1, lns_iters=40, seed=2`) with the full observation (`FullEnvObservation`) plans every train through its stops in time and space before the first step, then improves the plan by large-neighbourhood search; about two minutes in Python on Neu-Frankfurt and seven and a half on Köln, on two vCPUs. Its actions are in `data/<map>/planner_actions.json`, with the hash seed its run was scored under (`hash_seed`, section 4c); `replay.js` hands them to the engine, which simulates and scores them like any other run. `tools/check_plan.py --map <map>` reruns the planner and compares the actions.
  - *On Neu-Frankfurt* v2 gives the first version's plan, action for action: 597 steps, −1,014.0.
  - *On Köln* every train departs and arrives, without a collision, in 886 steps: −27,655.25. The six S-Bahn loops are done the moment they enter (section 2), and their 36 stops are the only ones it does not serve: 72 of the 108. Three of its stops are booked in Python's hash order (section 4c).

## 4a. The floor (`js/floor.js`, `tools/score_floor.py`)

The best score any dispatcher can reach on the map, bounded from below. For each train, a breadth-first search from its start over (cell, direction), never through its destination, gives the fewest moves to a platform of each timetabled stop and to the destination. A train is on the map at the earliest at step max(earliest departure, 1) + 1 and moves at most one cell every 1 / speed steps; halting, detours and other trains only add time, and a train that never arrives or never sets off pays more than a late one. A stop reached L steps after its latest arrival costs at least 0.5 × L (or the lost stop's penalty, 499.2 or 684, whichever is less), the destination L steps late costs L.

- **Neu-Frankfurt: 944.** Only the two S-Bahns of the airport loop are bound to be late (217 cells at two steps each, against a window of 267 steps), at least 472 points each.
- **Köln: 25,010.5.** The six S-Bahn loops start on their destination, so the search reaches none of their stops, and flatland agrees (section 2): 6 × 684 = 4,104 points each, 24,624 in all. Six local trains (RB süd 1–3, RB nord 1–3, two steps per cell) are bound to be late: 386.5 points between them.

`tools/score_floor.py` computes it on flatland's own rail (`get_transitions`, `get_new_position`, the agents' waypoints and latest arrivals); `tools/export_fixtures.py` writes it to `tests/fixtures/<map>/rules.json` and asserts that the two timing assumptions hold in every recorded run (no train on the map before max(earliest departure, 1) + 1, no move sooner than 1 / speed steps after the last). `js/floor.js` computes the same in the browser; `tests/guide.mjs` compares the two train by train on both maps, and a planted error in the browser's entry step is caught.

## 4b. When penalties are booked

`DefaultRewards.step_reward` books a collision when a moving train is brought to a halt without a stop action (936 or 1,282.5 × its speed at that moment, so a train already standing costs nothing more). A train's stops (served, late, early or lost) and its delay at the destination are booked by `_agent_done_or_max_episode_steps_reward` in the step it arrives, or at the end of the episode for a train still on its way or never started. The running score therefore lags behind what the map shows; the guide, the Score tab and the Method say so, and `tests/guide.mjs` checks the rule on every term of the four Python runs.

A stop counts as served when the train stood on any of the platforms its timetable lists for it. Two calls of one train at the same station can share platforms (Köln's RB süd and RB nord trains call at Stop 2 on the way to the hub and again on the way back, and five or six of the eight platforms, cell and direction, are listed for both calls), and then one halt on a shared platform counts for both: the reward function looks for each call's platforms in the train's arrivals. The page's timetable shows each stop at the platform the reward function books it at (`js/sim.js`), so a halt on a shared platform appears under both calls, while the events and the train's progress follow the platforms the train calls at. Where a train stood on two listed platforms of one stop, which of them is booked is a matter of Python's hash order (4c).

## 4c. Stops booked in Python's hash order

The reward function books an intermediate stop at `list(set(listed) & set(arrivals))[0]`. When the train stood on one listed platform, that is the one. When it stood on two or more, it is the first of a Python set of flatland's `Waypoint`, an attrs class (`@define(frozen=True)`) whose generated hash includes a string hash salted per process: which platform is booked depends on `PYTHONHASHSEED`. In Köln's optimized run this happens three times. RB nord1, RB nord2 and RB nord3 serve their first call at Stop 2 on (56, 80) facing west, one of the five platforms the timetable lists for both calls, and their second call on (57, 80) facing east, listed only for the second, both with a real stop. Booked at the shared platform, the second calls cost 0, 17.5 and 12.25 points: the trains reached it, during the first call, long before the second call's latest arrival, and RB nord2 and RB nord3 left it 10 and 7 steps before the second call's earliest departure (1.75 points a step; RB nord1 left it 4 steps after). Booked at their own platforms, they cost 8, 1 and 20.5 points, for arriving 16, 2 and 41 steps late.

The three are not booked independently. CPython builds `set.intersection` by walking the smaller of the two sets, here the call's listed platforms (eight of them, against the hundreds of cells each train has entered), and adds the matches to the result in that order. Calls that list the same platforms in the same order give sets with the same layout in one interpreter, and trains that stood on the same platforms get the same result, so one interpreter books every stop of such a group at the same platform. The three second calls at Stop 2 list the same eight platforms in the same order and their trains stood on the same two: one group, booked as one. The run can therefore score exactly two scores: −27,655.25 with all three at the shared platform (0 + 17.5 + 12.25 = 29.75 points) and −27,655.0 with all three at their own (8 + 1 + 20.5 = 29.5): the hash seed moves the score by a quarter of a point. Replayed under seeds 0 to 11, the run scored exactly these two: −27,655.25 under seeds 0–2, 6–8, 10 and 11, −27,655.0 under seeds 3–5 and 9. Neu-Frankfurt's runs and Köln's baseline have no such stop.

Under seed 0, the booking the page shows, the 29.75 points of Köln's optimized run for leaving stops early are two of these bookings, not early departures: booked at the platform shared with the first call, RB nord2's and RB nord3's second calls take the times of the halt there during the first call, although both trains stopped for their second calls on platforms of their own and left them after the earliest departure. No train of the run leaves a stop early.

- `tools/export_fixtures.py` (and `tools/check_plan.py`) run only under a fixed `PYTHONHASHSEED`; the exporter asserts that it is the plan's `hash_seed` and that the replayed plan scores the plan's `reward`. Its mirror of the reward function (`Decomposer`) builds the same set in the same process and so books the same platform; for every stop a train reached on two or more listed platforms it records, in `data/<map>/reference.json` under `runs.<run>.bookings`, `{ agent, stop, booked, options: [{ platform, value }] }`: the train, the stop (k, as in the terms), the platform Python booked as [row, column, direction], and for each listed platform the train stood on, in the timetable's order, what booking the stop there adds to the score. The seed goes into `hash_seed`. It also asserts, for every such stop, that the intersection walks the listed platforms (the train's arrivals are the larger set), which the grouping above needs.
- The engine (`RailEnv`, option `bookings`; `stopArrival`) books such a stop at the recorded platform. It reports (`ambiguous`) a stop reached on two or more listed platforms without a record, a record naming a platform the train did not reach, and a record for a stop reached on one platform; the page then withholds "same score as the Python runner" and shows its banner, and `tests/engine.mjs` fails. Its `bookings` case holds the record against the engine: exactly the recorded stops are reached on several platforms, the options are those platforms, the booked one among them, and booking the stop at each option adds exactly the recorded value. Then the scores the page says the run can have (`js/hashorder.js`, `hashOrder.groups` and `hashOrder.scores`): the test groups the recorded stops itself, from the map file's listed platforms per call and the record's options, checks that the record books each group at one platform, replays the run once for every choice of platform per group with all the group's stops booked there, and requires the page's scores to be exactly the scores of these replays. Three negative controls: a record naming the train's other platform changes the score; with no record, the engine's own first choice happens to give Python's score here, and only the report catches it; and scores worked out stop by stop, as if each stop were booked on its own, include six that no interpreter gives.
- The page groups the recorded stops from the record and the scenario (`js/hashorder.js`). The Method tab names the stops, gives the scores the run can have, each with its booking, and what the hash seed moves the score by, and says what the booking shown counts: RB nord2's and RB nord3's early departures, with the times of the first call's halt. Wherever such a stop shows in a penalty, the page points to the Method: the Score tab's and the Story tab's early departures ("Both: second calls booked at the first call's platform"), and a train's timetable, whose mark for such a stop says what is counted ("Counted as left 10 early") and whose note says where ("booked at the first call's platform, with its times").

## 4d. Malfunctions (the Malfunctions switch)

The challenge's loader can switch malfunctions on: `ParamMalfunctionGen(MalfunctionParameters(0.04, 2, 10))`. Its runner and the leaderboard run without them; the final ran with fixed disruptions of its own (T-Systems' whitepaper, October 2026), which are not public. What flatland 4.2.2 does with the loader's generator:

- **Every train draws in every step, whatever it does.** `MalfunctionEffectsGenerator.on_episode_step_start` calls `MalfunctionHandler.generate_malfunction` for every train, in the trains' order, at the start of `RailEnv.step`, before any action is read. `ParamMalfunctionGen.generate` takes the next of a million uniform numbers it drew from the environment's generator at its first call; below 1 − e^−0.04 (3.92 %) the train breaks down for `randint(2, 11) + 1` = 3 to 11 steps, drawn from the same generator. So the draws depend on the seed alone: the same for every dispatcher, and a dry run of the generator that never steps the environment makes exactly the draws of a real run.
- **A draw counts only between breakdowns.** `_set_malfunction_down_counter` sets the counter (and `num_malfunctions`) only when it is 0; a draw that falls on a train already broken down is lost. The counter goes down by one at the end of every step, for every train (`update_counter`), after the state machine and the reward.
- **A broken-down train stands.** With the counter above 0, the state machine sends a train on the network to `MALFUNCTION` (speed 0, no move, no crash penalty: MOVING to MALFUNCTION is not a halt), a train off it to `MALFUNCTION_OFF_MAP`; once the counter is 0 again it moves on if told to and allowed (else `STOPPED`), or enters the network from where it waits. A breakdown that hits a train in its last step still stops it there: the arrival waits. A train already done is not affected.
- **The seed.** The loader leaves the generator to the system's entropy (`random_seed=None`), so a run with malfunctions can only be repeated seeded: `env._seed(seed)` after loading and before `run_episode` (whose `env.reset()` keeps the generator). The page's runs use seed 1 on both maps, the first seed of the test below, fixed before any result was seen.

The engine (`RailEnv`, option `malfunctions`) takes the draws as `tools/export_fixtures.py` records them in `data/<map>/malfunctions.json`, `[[step, train, broken steps], …]` for every draw that breaks a train down over the map's whole episode (2,410 on Köln, 911 on Neu-Frankfurt), and applies a step's draws at its start as flatland does (`generateMalfunction`); the counter and the state machine were already ported. The browser cannot repeat numpy's Mersenne Twister and its seeding, so it replays the draws instead, as it replays the planner's actions: the exporter makes them in a dry run of the same seeded generator, asserts that each recorded run met exactly those, and the data suite reads every draw's effect off the Python traces' counters. The optimized run under malfunctions replays `data/<map>/planner_actions_malfunctions.json`, PlannerController v2's actions as it ran through the challenge's runner with that seed (`tools/check_plan.py --malfunctions`): it plans before the first step, when nothing has broken down yet, and from the first breakdown on (step 1 on both maps) follows its plan in its safe mode (`PathFollower`: planned routes, the planned order through every cell, every planned stop).

**The test over many seeds** (`tools/malfunction_test.py`, `data/<map>/malfunction_test.json`): the optimized run on seeds 1 to 100 and the baseline on 1 to 20, through the challenge's runner. ## 5. What the page adds on top (`js/sim.js`)

`simulate()` runs a controller through the engine once and keeps, for every step, each train's cell, direction, state, speed, whether it was blocked, how late it is, how long it has stood still and the stop whose platform it stands on; the running score per step and per train; every reward term (the engine's optional ledger, which changes no computation); the timetable as the reward function counts it (each stop at the platform it is booked at: the arrival there, the first halt and the departure); and the events, which follow the platforms the train calls at. Everything on screen reads from that record, so scrubbing the timeline costs nothing.

A train counts as **late** from the step it passes the latest arrival of the next stop it has not reached (or of its destination); **blocked** when the motion check refused its move; **stuck** when it has stood still for 40 steps and is 40 steps past its departure time. A train done in the step it enters (Köln's loops) counts as having entered and arrived in that step; it is never drawn on the map, and the Story tab tells it as one moment ("Done before it moves").

**How the map moves trains between steps** (`js/glide.js`, computed once per run as `run.paths`). Flatland keeps a train in one cell until its speed counter has covered the whole cell: an S-Bahn (0.5) takes two steps per cell, and a train setting off covers 0.3 and then 0.6 of a cell before it leaves its first one. The first release moved a hexagon only in the step its train changed cells, so these trains glided for one step and froze for the next although they never stopped: 821 such frozen steps in Neu-Frankfurt's optimized run, 192 in its baseline. Now a train rests at the centre of its cell in every step it stands, at the centre of every cell it enters at a steady speed (the speed of the step before) and does not halt in, and where it enters and leaves the map; between two of these rest points it moves in proportion to the distance its speed counter covers in each step, never more than a cell in a step. So a train glides at its own speed, slows into a stop and speeds up out of one, runs through cell centres at full speed exactly as before, and stands still, at its cell's centre, whenever the engine has it standing. Drawing the speed counter's distance itself was rejected: a train waiting behind another stands near the end of its cell, so the two hexagons would sit on top of each other. One real movement stays hidden: the optimized plan sometimes inches a waiting train forward inside its cell (halt, 0.3 of a cell, halt; 52 steps), which mostly lets it leave the cell with its first move once it may go; such a train is drawn standing. With reduced motion every train sits at the centre of its cell and jumps from cell to cell, as before. `tests/glide.mjs` checks all of this on the four runs of both maps against the Python traces.

## 6. Build decisions

- **Replay, not a port of the planner.** `PlannerController` v2 is several hundred lines of search over a time-expanded network and takes about two minutes in Python on Neu-Frankfurt and seven and a half on Köln; the page would wait or need a worker and a port that is hard to verify. Replaying its actions through the verified engine shows the same run and the same score, and `check_plan.py` ties the actions to the planner.
- **Hash-ordered bookings recorded, not guessed.** The browser cannot reproduce CPython's salted string hashes; the exporter records which platform Python booked instead (4c), and the engine follows the record only where the run left it a choice. The scores other seeds give come from how CPython builds the intersection, stops booked alike in groups, not from a bound that treats every stop on its own: that bound (−27,671.5 to −27,638.75 here) includes six scores no interpreter gives.
- **Words computed, not typed.** The guide (`js/guide-content.js`) and the Story tab (`js/story.js`) build every figure in their text from the scenario, the rules and the simulated runs; `tests/guide.mjs` and `tests/story.mjs` hold them against facts worked out independently from the scenario file, the challenge's own penalty code (`tests/fixtures/<map>/rules.json`, written by the exporter) and the Python traces.
- **Fixtures in the branch.** The Python traces of the eight runs (about 12 MB in `tests/fixtures/<map>/`, over half of it the runs with malfunctions) make the engine checks runnable without Python. The page never loads them.
- **An orphan `gh-pages` branch.** The site has nothing in common with the Python code on `main`, and GitHub Pages serves a branch's root as it is (`.nojekyll`).
- **No dependencies.** Vici's files are copied unchanged into `vici/`; everything else is plain ES modules. The Content Security Policy allows only this site, and no code uses `innerHTML`.
- **One map per page load.** The map is part of the address (`?map=frankfurt`, `?map=koeln`); an address without one, or with one the page does not know, opens the default map, Köln (`DEFAULT_MAP` in `js/maps.js`). The page writes the map into the address together with the run and the step, and the map switch names it too, so a shared moment keeps its map whatever the default. Links that named Köln (`?map=koeln`) work as before; links from before Köln became the default that named no map, then Neu-Frankfurt's, now open Köln. The switch in the header loads the other map's page rather than swapping data in place: every module reads its map once, and only the map on screen is simulated. `js/maps.js` (the page), `tests/lib/maps.mjs` (the tests) and `tools/maps.py` (the Python tools) list the same maps, files and runs, and `tests/data.mjs` holds the three together. Each map's files live in `data/<map>/` and `tests/fixtures/<map>/`.
- **The leaderboard's figure is fixed in `js/maps.js`** (−37,374, from the project brief); it is neither computed nor simulated. The page shows the same figure on both maps as the target to beat: in the KPI tile, the comparison of scores, the score chart's reference line and the guide. `tests/guide.mjs` and `tests/smoke.mjs` hold it to the brief's figure.
- **Köln's station names** come from its line names, as Neu-Frankfurt's do: the only places they mention are Essen and Frankfurt, so Stop 12 is Essen, Stop 18 Frankfurt and Stop 16, the end of the Frankfurt branch line (`ICE_Frankfurt_nebenstrecke`), Frankfurt (branch line); the other thirteen stations keep their numbers. The file never names Köln; the name comes from the challenge's final, which ran on maps of Frankfurt and Köln (T-Systems' whitepaper, October 2026).
