# Tests (optional, for developers)

Dispatch Lab itself needs no Node.js, npm, Python or build step. These scripts are the checks behind it: that the browser engine is the challenge's Python environment, that the page shows what the engine computed, and that it follows Vici. Run them after changing code or data. GitHub Actions runs the Node.js and browser suites on every push to this branch (`.github/workflows/tests.yml`).

Every suite covers both maps, Neu-Frankfurt (`frankfurt`) and Köln (`koeln`), each with two runs, the baseline and the optimized run, and each run twice: as the challenge's runner runs it, and with the challenge's malfunctions on (the page's Malfunctions switch, `?malfunctions=on`; `data/<map>/malfunctions.json` holds the seed and the generator's draws, `planner_actions_malfunctions.json` the plan under them, `fixtures/<map>/trace_<run>_malfunctions.json` the Python traces). The page opens on Köln; Neu-Frankfurt is `?map=frankfurt`. Their files are in `data/<map>/` (the map, the plan, the Python runner's scores) and `fixtures/<map>/` (the Python traces and the rules); `lib/maps.mjs` lists them, the same list as the page's `js/maps.js` and the Python tools' `tools/maps.py`. The Node.js suites that take arguments run one map when named (`node tests/engine.mjs --map koeln`, `node tests/story.mjs koeln`).

## The Python side

The fixtures come from the challenge's own Python environment. With a checkout of the challenge (its `uv` environment set up as its README says, flatland-rl 4.2.2):

```
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/export_fixtures.py --repo <challenge> --check   rebuild and compare, both maps
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/export_fixtures.py --repo <challenge>           rewrite tests/fixtures/<map>/ and data/<map>/reference.json
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/check_plan.py --repo <challenge>                each map's plan is PlannerController v2's
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/check_plan.py --repo <challenge> --malfunctions the same with malfunctions on (seed 1)
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/malfunction_test.py --repo <challenge> --map koeln --seeds 1-100 --live 3 --baseline 20 --out <dir> [--part 0/2]
PYTHONHASHSEED=0 <challenge>/.venv/bin/python -B tools/malfunction_test.py --repo <challenge> --map koeln --merge <dir>   writes data/koeln/malfunction_test.json
```

`export_fixtures.py` records every run twice, the second time with the loader's malfunctions and the environment's generator seeded with `tools/maps.py`'s `MALFUNCTION_SEED` (`--variant normal|malfunctions` for one of the two); it makes the generator's draws in a dry run that never steps the environment, asserts that every recorded run met exactly those, and writes them to `data/<map>/malfunctions.json`. `malfunction_test.py` runs both runs with malfunctions over many seeds (about an hour on two cores for 100 seeds of both maps, 37 minutes for Köln and 24 for Neu-Frankfurt, most of it the optimized runs and the live plans; the planner plans once per process, as it would on every seed, and the first seeds plan live as well to show the actions are the same).

Both scripts refuse to run without a fixed `PYTHONHASHSEED`: where a train stood on two listed platforms of one stop, the reward function books the stop at whichever comes first in a Python set, and that order follows the hash seed (`TECH_NOTES.md`, 4c). The plans were scored under seed 0 (`hash_seed` in `planner_actions.json`); the exporter checks that it runs under the same seed and records each such booking in `data/<map>/reference.json` (`hash_seed`, `runs.<run>.bookings`), which the engine then follows. Every script takes `--map frankfurt` or `--map koeln` to run one map. `export_fixtures.py` also writes the floor (`tools/score_floor.py`, on flatland's own rail) into `tests/fixtures/<map>/rules.json`, after checking the timing it assumes in every recorded run. `check_plan.py` replans each map (about two minutes for Neu-Frankfurt, seven and a half for Köln) and compares the actions with `data/<map>/planner_actions.json` (`--write` rewrites it); it needs the planner's two files (`planner_core.py`, `plannercontroller.py`) in `<challenge>/src/controller/`, which are not part of this repository. These scripts only wrap the runner to record what happens; they change nothing in the environment.

## Setup for the browser suites

You need Node.js 20 or later and Playwright with Chromium. Install them once, outside this folder:

```
npm install -g playwright@1.56.0
npx playwright install chromium
```

Then run with Node's module path pointing at the global packages:

```
NODE_PATH="$(npm root -g)" node tests/run-all.mjs
```

On Windows PowerShell: `$env:NODE_PATH = (npm root -g); node tests/run-all.mjs`.

Options (environment variables):
- `PLAYWRIGHT_MODULE`: path to a Playwright installation, instead of `NODE_PATH`.
- `CHROME_PATH`: use this Chrome or Chromium binary instead of Playwright's.
- `DL_TEST_OUT`: folder for screenshots (default: the system temp folder, `dispatch-lab-tests/`).

The suites serve the page on `127.0.0.1`: smoke on port 8765, layout on 8766, hexagon on a random one between 8790 and 9089. Every request to another host is blocked.
